raph-of-Skills Dependency Propagation — Deep Dive
Source: Liu et al., Graph-of-Skills: Dependency-Aware Structural Retrieval for Massive Agent Skills (arXiv:2604.05333v4, EMNLP 2026). Code: github.com/davidliuk/graph-of-skills.

1. The Problem Dependency Propagation Solves
Flat semantic retrieval finds skills that look related to the query. It often fails to find skills that are functionally required to run the top match:

Top semantic hit: a high-level “solver” or report generator
Missing: parser, converter, auth setup, preprocessor, schema loader

That gap is the prerequisite gap. Loading the full library closes it only by drowning the agent in tokens. Graph-of-Skills (GoS) closes it by propagating relevance along dependency structure, especially backwards from a matched skill to its upstream prerequisites.

2. Offline Substrate: Typed Skill Graph
GoS first converts a local skill corpus $\mathcal{C}$ into a typed directed graph:
$$G = (V, E, w, \phi)$$

Nodes $V$: normalized skill records (name, capability summary, I/O fields, tags, entrypoints, source path).
Edge types $\mathcal{R}$:
$\mathrm{dep}$ — executable prerequisites (primary)
$\mathrm{wf}$ — workflow / pipeline steps
$\mathrm{sem}$ — near-duplicate or topical adjacency
$\mathrm{alt}$ — interchangeable alternatives


How dependency edges are induced

Deterministic I/O overlap:Edge $v_i \rightarrow v_j$ if the outputs of $v_i$ are compatible with the inputs of $v_j$ above a fixed schema threshold (no LLM). Direction means: $v_i$ can supply an artifact that $v_j$ consumes.
Sparse LLM validation:For each node, form a small candidate pool (lexical + semantic + I/O expansion, top-$k$ default 8). Batch-validate only those candidates. Construction cost is $\mathcal{O}(Nk)$, not $\mathcal{O}(N^2)$.

So the graph encodes executable structure, not merely topical similarity.

Stage 1 — Hybrid seeding
Dense retrieval is strong on the visible top-level skill; lexical retrieval is strong on filenames/artifacts. GoS merges them:
$$z_i(q) = \eta\, s_i^{\mathrm{sem}}(q) + (1-\eta)\, s_i^{\mathrm{lex}}(q)$$
$$\mathbf{p}_i = \frac{z_i(q)}{\sum_j z_j(q)}$$
$\mathbf{p}$ is the personalization / restart distribution for PageRank: probability mass starts on skills that already match the query.
Stage 2 — Reverse-aware typed diffusion (the core)
For each relation type $r$, define:

Forward transition $T_r^{\rightarrow}$ from adjacency $A_r$ (row-normalized)
Reverse transition $T_r^{\leftarrow}$ from $A_r^\top$ (row-normalized)

Unified transition operator:
$$T = \operatorname{RowNorm}\!\left(
  \sum_{r \in \mathcal{R}}
  \lambda_r \bigl( T_r^{\rightarrow} + \gamma_r\, T_r^{\leftarrow} \bigr)
\right)$$

$\lambda_r$: relative weight of relation type ($\sum \lambda_r = 1$)
$\gamma_r$: how strongly reverse traversal is allowed for type $r$(dependency edges typically get high $\gamma_{\mathrm{dep}}$)

Personalized PageRank iteration:
$$\mathbf{s}^{(\ell+1)} = \alpha\,\mathbf{p} + (1-\alpha)\, T^\top \mathbf{s}^{(\ell)}$$

$\alpha \in (0,1)$: restart probability (teleport back to seeds)
At convergence, $\mathbf{s}^\star$ scores every skill by a mixture of:
direct query relevance (via $\mathbf{p}$)
multi-hop structural importance under reverse-biased walks


Why “reverse” matters conceptually
Suppose the seed is a high-level ReportGenerator that depends on CSVParser and AuthSetup:
textKopierenKopiertAuthSetup ──dep──► CSVParser ──dep──► ReportGenerator  (seed)

Forward walks from the seed go downstream (consumers of the report) — often useless.
Reverse walks go upstream along dependency edges and raise the score of CSVParser and AuthSetup even if they are weak semantic matches to the user query.

That is the mechanism that closes the prerequisite gap.
Stage 3 — Budgeted reranking and hydration
Diffusion score is mixed with direct field matches:
$$\rho_i(q) = \mathbf{s}_i^\star + \mu\, m_i(q)$$
Skills are hydrated (materialized as agent-consumable payloads: path, capability text, execution notes) in descending $\rho$ order under:

per-skill character/token cap
global context budget $\tau$

The formal target approximated by this pipeline is the budgeted selection problem:
$$\max_{B \subseteq V}
\sum_{v \in B} \mathrm{rel}(v,q)
+ \beta \sum_{(u,v) \in E_{\mathrm{dep}}} \mathbb{I}[u \in B \land v \in B]
\quad \text{s.t.}\quad \mathrm{cost}(B) \le \tau$$
Relevance + dependency completeness under a hard prompt budget (quadratic knapsack → approximated by seed → reverse PPR → budgeted hydrate).

5. End-to-End Performance Context
Across SkillsBench and ALFWorld, three model families (Claude Sonnet 4.5, MiniMax M2.7, GPT-5.2 Codex):

GoS achieves the highest average reward in all six model–benchmark blocks.
SkillsBench + GPT-5.2 Codex: +7.0 absolute reward vs full library loading (+25.6% relative), −56.7% total tokens.
Library-size sweep (200 → 2,000 skills): advantage emerges once the library exceeds a few hundred skills — the regime where full loading becomes toxic and flat retrieval starts missing prerequisites.

Typical retrieval interface in experiments: at most $N=8$ hydrated skills, 2,400-character per-skill cap, 12,000-character global cap (shared with the Vector Skills baseline so embedding quality is not a confound).

GoS is the cleanest empirical demonstration that direction of walk on a skill dependency graph is a first-order design choice: reverse bias recovers executable prerequisites; forward bias can actively hurt.

7. Practical Implications for a Harness

Build a dependency graph offline from I/O schemas (deterministic) plus sparse validation; do not rely on metadata similarity alone for edges.
Seed with hybrid signals, then bias transition weights toward reverse dependency edges when running PPR (or any diffusion).
Treat forward-only graph expansion as a harmful default — ablations show it underperforms even “no graph.”
Hydrate under a hard budget; diffusion ranks candidates, it does not dump the whole neighborhood into context.
Compose with other routers: e.g., SkillWeaver-style decomposition for multi-step queries, then GoS-style reverse expansion per sub-goal; or SkillRouter body-aware rerank on the final GoS candidate set when skills are highly overlapping.


8. Limitations and Open Questions

Graph quality depends on I/O schema coverage; poorly documented skills yield weak or missing $\mathrm{dep}$ edges.
Fixed offline graph vs skill churn (SkillDAG-style online edge proposal is complementary).
Hyperparameters $\lambda_r, \gamma_r, \alpha, \eta, \mu$ are important; the paper reports defaults and type-specific reverse weights but production tuning may be domain-specific.
Evaluation libraries are still in the hundreds-to-low-thousands; behavior at SkillRouter’s ~80K scale with dense near-duplicates is not fully characterized.
Dependency-pair co-recovery is a strong intermediate metric; full causal claims about “why” reward improves still rest on the reverse vs forward ablation.

If you port GoS into a production skill-routing plane, the evidence-backed starting point is:

Tune first if needed: reverse dependency strength and seed set size / top-$N$ under your context budget.
Tune later / less critical: $\zeta$, PPR tolerance, exact $\eta$/$\mu$ (unless you observe topical drift or seed collapse).
Avoid: forward-only diffusion, pure semantic seeding, or very large reverse weights on semantic/alternative edges (invites drift).

6. Open Gaps

No published sensitivity curves for $\alpha$, $\eta$, $\mu$, or continuous $\gamma_{\mathrm{dep}}$.
Relation-type $\lambda_r$ after normalization is implicit in the relative forward weights; exact post-normalization mass per type is not tabulated.
Whether defaults remain optimal at SkillRouter-scale (~80K highly overlapping skills) is untested in the GoS paper.
Interaction with body-aware rerankers (SkillRouter) or compositional decomposers (SkillWeaver) is left to integrators.

Bottom line: GoS is intentionally configured with a small, stable hyperparameter set. The only hyperparameter group with strong causal evidence of first-order impact is reverse dependency traversal strength ($\gamma_{\mathrm{dep}}$ high, not zero). 6. Qualitative Counterexamples (Important for Interpretation)
The paper’s trajectory analysis notes asymmetric failure modes:

GoS helps when the required neighborhood exists and is connected (e.g. pedestrian-traffic-counting pipeline recovered cleanly).
GoS can fail when the graph recovers only a partial stack that Vanilla’s full library still contains (e.g. earthquake-phase-association: Vanilla passed, GoS failed).

So reverse PPR improves average reward by assembling executable neighborhoods more often; it does not dominate on every task. Structural retrieval is only as good as graph coverage of the true prerequisite set.

8. Methodological Critique
What is done well

Mechanism isolation via budget-matched offline study.
Explicit forward vs reverse control (not just “with/without graph”).
Intermediate structural metric $D$ aligned with the prerequisite-gap thesis.
Library-size sweep shows when the method is worth using.
Honest qualitative failures.

What remains weak or missing

Component ablation only on one model × one library size.
No significance tests on end-to-end reward cells.
No continuous ablations of $\alpha$, $\eta$, $\mu$, or per-type $\gamma_r$ (only all-reverse-off).
Offline matched study uses lexical-only seeds and 200 skills — not a perfect parallel of the 1k hybrid-seed agent runs.
Interaction with body-aware rerankers (SkillRouter-style) or multi-step decomposers (SkillWeaver) not ablated.
Graph build variance is partially controlled (3 builds) in Study B but not fully reported for Study A.


9. Practical Takeaways from the Ablations

Never ship forward-only dependency expansion under a tight skill budget.
Measure dependency-pair co-recovery, not only Hit@k / reward, when tuning graph retrieval.
Invest in seed quality (hybrid lexical + semantic) before adding more diffusion.
Prefer GoS-style routing once the library is hundreds+ of skills; for ~200, full loading may still win.
Prioritize skill documentation quality (descriptions + I/O) over fine-tuning $\zeta$.
Expect task-level variance: incomplete graphs can make selective retrieval lose to “load everything.”


10. Bottom Line
The Graph-of-Skills ablation package is unusually clear for this field. It supports a precise claim:
Under a fixed context budget, reverse-aware Personalized PageRank over a dependency-typed skill graph improves executable bundle coherence (and downstream reward) relative to flat retrieval; forward-only diffusion is worse than no graph; one-hop expansion is approximately useless on sparse graphs; and the advantage appears once libraries leave the small-N regime.
That is a stronger, more falsifiable mechanism story than “graphs help skill routing.” The main residual risks are limited model/size coverage for the component table and the absence of continuous hyperparameter ablations beyond the binary reverse-off switch.
