# ADR-006 — State Ownership Classes for the Enterprise Agent Harness (PROPOSED)  - **Status:** **PROPOSED** (research-backed, undecided). Not accepted; requires a named human decider. - **Deciders:** *unassigned* — harness architecture owner (this ADR was authored by a research agent and has no   decision authority of its own). - **Cross-references:** `docs/research/state-ownership/2026-09-18-enterprise-agent-state-ownership-v0.1.md`   (evidence, matrices, falsifiers); `docs/research/state-ownership/state-ownership.kb.jsonl` (50 claims);   `docs/governance/2026-09-18-state-ownership.missing-assumption-blocker-ledger.md` (open items). - **Note on repository scope:** this ADR concerns a planned *agent harness* architecture. It is recorded in this   repository only because that is where the research deliverable lives; it does not change the FuFirE engine's   behaviour, contracts or data model in any way.  ## Context  The planned harness pipeline is `Task → Capability Selection → Capability Contract → IR/Manifest → Runtime → State Refresh → Preconditions → Authorization → Execution → Validation → Commit/Recovery`. The open question was what "state" means at each step, and how the harness prevents an LLM from treating stale context, memory, cached tool results or earlier snapshots as current authoritative truth.  Evidence reviewed (report §2) includes: model degradation with context length and multi-turn underspecification (S1/S2), unreliable rule adherence in tool-agent benchmarks (`pass^8 < 25%`, S5), policy/authorization staleness ("new enemy problem", S8), impossibility results for lost-update prevention in highly available systems (S9), invariant confluence as the necessary-and-sufficient condition for coordination-free correctness (S10), idempotency/outbox practice (S18/S19), memory poisoning and negative transfer results (S20–S23), and the repo's own unrepresentability precedent (S33).  ## Options considered  1. **Conversation/context as state** — rejected: no authority, no provenance, ages silently (report §5.4 model A). 2. **Single mutable agent state object** — rejected beyond Profile A: no distinct authority or lifecycle rules. 3. **Run state + external sources of truth** — partial; insufficient for durable workflows and effects. 4. **Run + durable workflow + external (recommended core)** — adopted as the proposal, with event sourcing    demoted to a storage option for workflow state. 5. **Four primitives + two projections + two registries** (the proposed refinement of 4): EXTERNAL/POLICY/WORKFLOW/    DERIVED plus EFFECT_LEDGER; WORKING_CONTEXT and RUN_VIEW as projections; EPISODIC log and PROCEDURAL registry as    registries.  ## Decision (PROPOSED)  Adopt, subject to human ratification and to the falsifiers in the research report:  1. State is modelled as an addressable binding (subject+aspect+source+revision|UNKNOWN+observation); no bare values. 2. Four orthogonal authority dimensions are declared per state type: epistemic, storage, write, decision    responsibility. 3. The primitive state classes are EXTERNAL_AUTHORITATIVE, POLICY, WORKFLOW, DERIVED, plus the EFFECT_LEDGER;    WORKING_CONTEXT is a projection; EPISODIC memory is a log view; PROCEDURAL memory is a pinned registry;    ARTIFACT is a content-addressed external subtype. 4. The LLM proposes; it never commits an authoritative external mutation directly. 5. Freshness is a relation evaluated in one of four modes (REVISION_VERIFIED, EVENT_VERIFIED, TIME_BOUNDED, UNKNOWN);    time-based age is a detector/fallback, never the general definition. 6. W2/W3 writes carry `expected_revision` + a stable `effect_id`; `UNKNOWN_COMMIT` is reconciled against the ledger. 7. Authorization decisions are taken at the effect boundary against a recorded policy revision; unknown freshness    fails closed for high blast radius. 8. Memory is authoritative only for the harness's own history and pinned procedures (`WORLD_CURRENT` illegal). 9. Derived artefacts carry `derived_from[]` with source revisions and a derivation version. 10. State contracts (v0.1, PROPOSED_STANDARD) are the type-level artefact; capabilities declare only requirements;     the manifest carries runtime-bound observations and refresh obligations.  ## Consequences  **Positive:** named failure classes (stale context, stale authorization, lost update, memory-as-truth, derived drift, cross-run contamination, TOCTOU, retry duplication) each map to a concrete mechanism; decisions become explainable from stored provenance; profiles A/B/C give a smallest-sufficient model per risk class.  **Negative / costs:** additional artefacts (contracts, ledger, provenance records); refresh traffic and latency; schema discipline that will feel heavy for small tasks (mitigated by the Profile A minimal model and the zero-state capability exemption).  **Explicitly NOT decided here:** numeric TTLs/timeouts/budgets (none are proposed); the choice of workflow engine; whether the authorization platform can supply consistency tokens (blocker BLOCKER-001); and the ratification itself.  ## Alternatives if this is rejected  Rejecting this ADR means choosing between (a) resource-API-only integration without contracts, (b) a single mutable run state, or (c) context-as-state. EXECUTIVE CONCLUSION  ## 1.1 The five load-bearing findings  **F1 — "State" is not a value; it is an addressable, attributable binding.** `[DESIGN_RECOMMENDATION, supported by STANDARD/ENGINEERING_PRACTICE]` A state value is unusable for a consequential decision unless it is bound to (identity, source, revision or an explicit `UNKNOWN` revision, observation event, observer). Evidence: HTTP defines validators (`ETag`) and conditional requests precisely because a bare representation is not a decision basis (S11); Kubernetes rejects any write whose `resourceVersion` does not match (S17); Zanzibar carries an opaque consistency token per check (S8). The equalities the quality gate demands — *current value ≠ observed value*, *write ≠ committed state change*, *read ≠ validated read* — are therefore **type errors that a schema can make unrepresentable**, not discipline problems. In-repo precedent: the FuFirE engine's `DerivedFieldStatus` has no `value` field at all, so a fabricated "verified" value is structurally impossible (S33).  **F2 — Authority is four orthogonal dimensions, not one.** `[DESIGN_RECOMMENDATION]` The harness must separate, per state artifact: (i) *epistemic authority* (whose statement wins when two values disagree), (ii) *storage ownership* (who persists the bits), (iii) *write authority* (who may mutate, and under which preconditions), (iv) *decision responsibility* (which principal is accountable for the effect). The prompt's H12/H13 are confirmed and extended: "authoritative", "owned" and "writable" are pairwise independent. Zanzibar is a clean example: the ACL store owns the data, the client service is the storage owner of the *content*, and the check service is epistemically authoritative for the *permission decision* — three different owners for one decision (S8). Kubernetes is another: controllers own *desired* state, the API server owns *recorded* state, `resourceVersion` is the merge authority (S17).  **F3 — The 10-category ontology reduces to four primitives plus two projections (+2 cross-cutting registries).** `[DESIGN_RECOMMENDATION, falsifiable]` After removing overlaps (§5), the classes that need their own lifecycle, authority rule and store are: **(1) EXTERNAL_AUTHORITATIVE_STATE** (systems of record, incl. artifact version stores addressed by digest), **(2) POLICY_STATE** (separated for *mechanism* reasons, not taxonomy reasons — see F4), **(3) WORKFLOW_STATE** (durable control state; `RUN_STATE` is its attempt-scoped view, not a peer class), **(4) DERIVED_STATE** (caches, indexes, summaries, materialized views, semantic-memory abstractions, embeddings). `WORKING_CONTEXT` and `ARTIFACT_STATE` are **projections**, not stores: context is a projection *into the attention budget*, artifacts are external state *whose version store is a content-addressed external system*. Episodic memory is a **log view**; procedural memory is a **pinned configuration/capability artifact**. §5.3 gives the merge criteria and what would falsify each merge. This is a deliberate reduction: seven of the ten proposed categories do not earn an independent store.  **F4 — Policy state is separated because it is self-referential and fail-closed, not because "policy" is a nice word.** `[PEER_REVIEWED_RESULT + ENGINEERING_PRACTICE]` Authorization is the one state class where a stale read *grants* authority instead of merely misinforming. Zanzibar's "new enemy problem" is the canonical failure: a permission removal and a content addition can be reordered by caching, so the removed user gains access to the new content (S8). Security practice converges on the same rule: high-risk/irreversible actions get a fresh, fail-closed check, revocation has a *propagation* window that must be measured as a security property, and a cryptographically valid token can still carry an operationally stale authorization decision (S28-adjacent practice, S8). Therefore policy state gets: causal/external consistency at the *effect boundary*, a recorded policy revision per effect, and `UNKNOWN` freshness ⇒ deny for high blast radius.  **F5 — Freshness is a relation between a requirement and an observation, not a property of data.** `[DESIGN_RECOMMENDATION + FORMAL_RESULT support]` "Fresh" has no meaning without (a) the consumer's requirement, (b) the source's ability to expose a version/change signal, (c) the invariant the decision can violate. `age < X seconds` is **not a general freshness definition**; it is a fallback that is only sound as a bound on *undetectable change* when the source cannot report revisions. This has a formal counterpart: coordination (and thus strong consistency) is required exactly where an application invariant is not coordination-free — invariant confluence gives a necessary and sufficient condition (S10), and highly-available transaction semantics *cannot* prevent lost update at all (S9). Consequence: per operation, freshness/consistency requirements must be **derived from invariants at risk and irreversibility**, not assigned by state-category name.  ## 1.2 The seven most important non-findings (what this research did *not* establish)  | # | Non-finding | Why it matters | | --- | --- | --- | | N1 | **No agent-specific measurement** was found that quantifies how much *pre-effect live refresh* reduces real task failures versus snapshot planning. | H5/H14 stay `DESIGN_RECOMMENDATION` with strong theoretical and engineering support, but with **no effect size**. STATE TERMINOLOGY / ONTOLOGY  ## 3.1 Working definition  > **State** is an *addressable, attributable binding* between (a) a logical subject, (b) a value or status, > (c) a source, (d) a version indicator or an explicit `UNKNOWN`, and (e) an observation event. > `[DESIGN_RECOMMENDATION, INFERENCE from STANDARD/ENGINEERING_PRACTICE S8/S11/S17]`  Corollary (the addressability axiom): **a bare value is not state.** "priority = high" is not state; "customer 4711 (CRM `crm.example`), revision `194`, `priority=high`, observed 2026-09-18T09:14Z by run `R7` via live read" is state. Everything the quality gate demands (`current ≠ observed`, `read ≠ validated read`, `write ≠ commit`) follows from this: those pairs differ in *agency inside the binding*, and a schema that cannot express the difference will lose it.  ## 3.2 Identity layer (research stream 1)  Three distinct identities must never be conflated. This is the single most common source of stale-write and stale-read bugs found in the mechanism literature (S17, S11):  | Layer | Question answered | Typical carriers | Lifetime | Consequence if confused | | --- | --- | --- | --- | --- | | **L1 logical object** | *What is being talked about?* | `resource_id`, URI, `workflow_id`, `customer_id`, MCP resource URI / URI template (S15) | long | writes land on the wrong entity; references rot silently | | **L2 concrete version** | *Which state of it?* | `revision`, `generation`, `ETag`, commit digest, `resourceVersion`, sequence number, event offset | until next write | lost updates; "read" silently mixed with "read some other version" | | **L3 runtime observation** | *When/by whom/under which mode was it seen?* | `observed_at`, `observer` (run/attempt/tool), `mode` (live/snapshot/cache/memory), `consistency_token` (zookie-analogue, S8) | per read | TOCTOU; audit cannot answer "on what state was this decision based?" |  Semantics fixed here:  - **`current(x, t)`** = the value the *source of truth of the relevant aspect* would return at time `t`   (by definition of that source). `current` is therefore **not** a property the harness can observe;   it can only observe `observed(x, t, source, mode)`. - **`revision`** = an opaque, source-defined token that changes whenever the source considers the resource changed. STATE CLASSIFICATION RESULT  ## 5.1 Orthogonality audit of the proposed ontology  The proposed ten categories are **not orthogonal**. Four axes are being mixed:  | Axis | Categories that actually live on this axis | | --- | --- | | **Ownership/locus of authority** (who can be right) | External State, Policy State, Artifact State, Run/Workflow State | | **Epistemic status** (how the value came to be believed) | Derived State, Semantic Memory, Episodic Memory, Working Context | | **Lifetime/durability** (how long it must survive) | Working Context (inference-scoped), Run State (attempt-scoped), Workflow State (process-scoped), Memory (indefinite) | | **Functional role in the pipeline** (what decision it feeds) | Policy State (authorization), Procedural Memory (capability selection/execution), Artifact State (deliverables) |  Concrete overlaps found:  1. **Artifact State ⊂ External State (special case).** Artefacts (files, code, documents, models) are external    state whose source-of-truth mechanism is a *version store* (Git, object-store versioning, model registry).    Their identity is content-addressed (digest/commit), which makes them a *strong* subcase, not a peer class. 2. **Derived State ⊃ (semantic memory abstractions, summaries, embeddings, indexes, materialized views, caches).**    Semantic memory *is* derived state with a memory-shaped lifecycle; treating them as peers duplicates invalidation logic. 3. **Episodic Memory ⊂ Log/History.** Episodic memory is a *query pattern over an append-only record*, not a    separate store with its own authority. Its authority is "what was observed", which is exactly the log's authority. 4. **Run State ⊂ Workflow State (attempt view).** If workflow state is event-sourced, run state is a materialized    view over one attempt. If it is not, run state is still a bounded sub-record of the process record. Two stores are    justified *only* for the durable-execution reasons in §10, not by ontology. 5. **Policy State ⊂ External State (mechanically) but must be split (semantically).** Nothing about ACLs/roles makes    them a different *kind* of data; what differs is that policy decides authority and its failure mode is    *grant-by-staleness*. The split is justified by mechanism (self-reference + fail-closed + causal ordering), and    this report states that explicitly instead of pretending the taxonomy is orthogonal. 6. **Procedural Memory ⊂ Artifact State (pinned configuration) with a distinct trust rule.** Skills/playbooks are    versioned artefacts that *direct action*; their risk is drift/misapplication (S22/S23), so they need approval    pinning, not freshness. 7. **Working Context overlaps everything** because it is a **projection** (§9), not a store. Calling it a state class    is the root cause of the failure class the prompt is worried about.  ## 5.2 Keep / merge / add  | Proposed category | Decision | Rationale | | --- | --- | --- | | WORKING_CONTEXT | **Reclassify as projection** | it is a view over other state plus directives; SOURCE-OF-TRUTH MODEL  ## 7.1 The rule that makes "source of truth" usable  `[DESIGN_RECOMMENDATION, INFERENCE from S8/S11/S17/S13]`  > A source-of-truth declaration is only meaningful as a **quadruple**: > `SoT(aspect, interval, consumer_class, mechanism)`. > "X is the source of truth" without aspect, interval and mechanism is not a statement this architecture accepts.  | Element | Why it is required | Failure if omitted | | --- | --- | --- | | **aspect** | one record has many aspects owned by different systems | "customer status" vs "customer credit limit" resolve to different authorities; a merged record silently mixes them | | **interval** | authority is "since the last authoritative write", not eternity | superseded data keeps winning conflicts | | **consumer class** | an audit consumer needs the frozen historical record; an executor needs the current one | audit and execution read the same field with different correctness conditions | | **mechanism** | conflict must be resolved *by a procedure*, not by convention | "CRM wins" is unenforceable; `If-Match`/revision comparison is enforceable (S11) |  ## 7.2 Sources of truth *are plural per record* (aspect registry)  | Aspect (example) | SoT | Interval semantics | Mechanism | | --- | --- | --- | --- | | `customer.priority` | CRM | since last CRM write | revision compare + `If-Match` | | `customer.credit_limit` | ERP/finance | since last finance write; finance write is authoritative even if CRM has an older copy | finance revision + policy rule | | `customer.consent.marketing` | consent service | since last consent event; **revocation is immediate, grant is explicit** | event offset, fail-closed on unknown | | `issue.state` | issue tracker | since last transition | revision/etag | | `repo.branch.head` | Git remote | since last push | commit digest | | `deployment.production_version` | deploy system | since last successful deploy | deployment id | | `permission(user, resource)` | authz service | since last relation write, with causal ordering w.r.t. content | consistency token (S8) | | `skill.version_in_use` | skill registry pin | since the pin was set by an approved process | semantic version + approval record |  Consequence: the harness must model **aspects**, not only records. A `StateRead` names an aspect; a `StateWrite` names an aspect; an aspect has exactly one SoT *per interval*. This is the operational meaning of "single source of truth — for this aspect, at this time, for this consumer".  ## 7.3 Can the agent ever be the source of truth?  `[DESIGN_RECOMMENDATION + empirical support S5/S20/S24]` — the answer is a scoped **no**:  | Proposition | Who is the SoT | Can the agent be? | | --- | --- | --- | | "the CRM priority is high" | CRM (external) | **no** — agent may read/propose only | | "the deployment succeeded" | deploy system | **no** — agent may trigger and read | | "the permission is granted" | authz service | **no** — agent may request | | "the agent proposed action A with rationale R at t" | harness effect/proposal ledger | **yes** — this is the agent's own history and it *must* be authoritative, because the agent itself is the only witness | | "the user asked X" | conversation/log record | **yes** (record of the utterance) — not a claim about the world | | "the artefact produced by this run is version v" | artifact store | **no** — the store owns it; the agent only requested the commit | | "the skill S version 1.4 was approved by principal P" | registry/approval record | **no** |  So the correct split is not "agent vs no agent" but: **epistemic authority** (never, for world facts) · **execution authority** (bounded by policy and by the capability contract) · **storage ownership** (only for its own proposal/history records, which the harness stores on its behalf, not the model).  ---  # 8. WORKING CONTEXT vs AUTHORITATIVE STATE  ## 9.1 Working Context is a projection  `[DESIGN_RECOMMENDATION, supported by S26 (lossy belief state), S1/S2 (degradation), S24 (stale evidence)]`  ``` WorkingContext(t) = Project( Directives, [StateRef_i], [Evidence_j], [Derived_k], CompressionPolicy )                      where every element carries: {source, revision, observed_at, mode, authority_class, taint} ```  - **Directives** (task, policy text, capability contract, manifest) are *instructions*, not state; they are not   falsifiable by a read and therefore must be typed separately (`DIRECTIVE`). Confusing a directive with state is   how stale context becomes an *instruction violation* rather than a stale read. - **StateRefs** are references; the *value* carried alongside is a convenience copy that expires the moment the   reference is refreshed (or when the refresh obligation fires). - **Evidence** (tool outputs, retrieved documents, prior observations) is historical by nature: it is authoritative   *as evidence*, never as current state. - **Derived items** (summaries, embeddings' text forms, model-produced notes) are the most dangerous class because   they *look* like state while having the weakest authority.  ## 9.2 Minimum provenance set per context item  | Field | Required for | Purpose | | --- | --- | --- | | `item_id` | all | stable reference for the audit trail ("on which item was this based?") | | `item_type` ∈ {DIRECTIVE, STATE_REF, EVIDENCE, DERIVED, MEMORY} | all | prevents the category error in §9.1 | | `source` + `source_kind` | STATE_REF/EVIDENCE | authority resolution | | `source_revision` (or `UNKNOWN`) | STATE_REF/EVIDENCE/DERIVED | staleness detection without time reasoning | | `observed_at` + `mode` | STATE_REF/EVIDENCE | distinguishes "was true at t" from "read at t" | | `authority_class` | STATE_REF/EVIDENCE | who wins conflicts | | `freshness_status` + `freshness_evidence` | STATE_REF/DERIVED | harness gating; audit | | `allowed_uses` | all | e.g. `PLANNING_ONLY`, `EFFECT_DECISION_ALLOWED`, `EVIDENCE_ONLY` | | `taint` / `trust` | EVIDENCE/MEMORY/DERIVED | poisoning containment (S20/S28 ASI06) | | `supersedes` | EVIDENCE/DERIVED | contradiction handling instead of silent replacement |  Model-side effect is **unverified**: no study was found showing that models *reliably act on* these markers (N6/C12). FRESHNESS / STALENESS MODEL  ## 14.1 Definitions (fixed, used throughout this document)  Let `o` be an observation `{subject, aspect, source, value, source_revision, observed_at, mode, consistency}` and `r` a requirement (§14.5).  | Term | Definition | Detectable by | | --- | --- | --- | | **FRESH** | `eval(o, r) = SATISFIED`: the observation's revision/event basis still covers the state as of the decision time per `r` | revision compare / event offset / (only if `r.mode = TIME_BOUNDED`) age bound | | **STALE** | `eval(o, r) = VIOLATED` **and** the violation is decidable (e.g., source revision moved, or age exceeded a `TIME_BOUNDED` bound) | same | | **UNKNOWN_FRESHNESS** | freshness cannot be evaluated (source exposes no revision; event stream unavailable; read failed) | absence of evidence ⇒ treat as unusable for effect decisions unless policy says otherwise | | **INVALIDATED** | a *derived/memory* artefact whose dependency revision set no longer matches the current bindings | dependency compare | | **EXPIRED** | a policy-imposed usability window has passed (lease/TTL/consistency-token window) regardless of revision equality | policy timer |  The distinction matters: **STALE** and **INVALIDATED** are *evidence-based*; **EXPIRED** is *policy-based*; **UNKNOWN** is an *epistemic admission*. NEGATIVE EXAMPLES (failure classes with mechanisms)  Format per example: **Scenario → false assumption → mechanism → which element prevents it → residual risk → falsifier.**  ### NEG-1 STALE_CONTEXT — model decides on an outdated tool result **Scenario**: agent reads ticket status `OPEN`, plans a comment, another user closes the ticket, agent posts a "still open" escalation. **False assumption**: "the tool result in context is current." **Mechanism**: tool results are *evidence*, and evidence ages; the plan had no refresh obligation. **Prevented by**: `allowed_uses=PLANNING_ONLY` for tool results + `pre_effect_refresh` on the write's precondition aspect + `expected_revision` (S11/S17). **Residual**: a refresh can itself be stale between read and write (narrowed by CAS). **Falsifier**: a workload where tool results are immutable (e.g. reading a commit blob by digest) — there the refresh obligation is unnecessary and should not fire.  ### NEG-2 STALE_AUTHORIZATION_STATE — policy changed, agent uses an old snapshot **Scenario**: an entitlement is revoked at 10:00; the agent (with a cached policy decision from 09:58) performs an action at 10:01. **False assumption**: "the last policy check is still valid." **Mechanism**: the "new enemy problem" (S8) — permission changes and content changes can be reordered without external consistency; revocation has a propagation window. **Prevented by**: fresh policy check with consistency token before W2/W3 + `on_unknown=DENY` + recorded policy revision per effect. **Residual**: revocation propagation is a measured property, not a binary (`revocation_completion_time`); cached bounded-staleness reads are acceptable only for low blast radius. **Falsifier**: a deployment where capability revocation can be proven instantaneous and observable by the harness.  ### NEG-3 LOST_UPDATE — agent overwrites a parallel change **Scenario**: agent reads CRM record (rev 194), human edits it (rev 195), agent writes its own version based on 194. **Mechanism**: unconditional write (no `If-Match`, no CAS). **Prevented by**: `expected_revision` + atomic compare at source (S11/S17); where the source lacks CAS, single-writer serialization is the only sound option (S9). **Residual**: merge conflicts still need a decision (rebase/reject) and a semantic merge rule. **Falsifier**: writes that are provably commutative/absorbing (I-confluent, S10) genuinely need no compare.  ### NEG-4 MEMORY_AS_TRUTH — long-term memory contradicts the system of record **Scenario**: semantic memory says "customer prefers email"; the CRM says "do not contact"; the agent sends email. **Mechanism**: memory treated as current world state; no re-verification; no conflict record. **Prevented by**: `authority_scope` (memory never `WORLD_CURRENT`), mandated re-verification for anything gating an effect (C5/§12.2), conflict surfacing (R-C3). **Residual**: memory may still *shape* the plan (advisory) and thus bias the agent toward the wrong action. **Falsifier**: a memory architecture that is demonstrably more current than the SoT for that aspect (then the SoT is the problem, not the memory).  ### NEG-5 DERIVED_STATE_DRIFT — summary/index built on a superseded revision **Scenario**: a "customer health" index was built from data at revision set R0; the source moves to R1; the agent acts on the index. **Mechanism**: no dependency tracking ⇒ no invalidation; index lag looks like truth. **Prevented by**: `derived_from[]` + `validity_basis` + verification-on-use for effect-gating derived values (§13.3). **Residual**: partial recompute and schema drift can preserve a *plausible* wrong value. **Falsifier**: a derived store that provably maintains exact revision coverage and is verified against the SoT at use time.  ### NEG-6 CROSS_RUN_CONTAMINATION — one run's state affects another **Scenario**: two runs of different tenants share an agent scratch directory or a global memory; run B sees run A's record identifiers and writes to the wrong entity. **Mechanism**: global mutable scratch/memory without scope enforcement. **Prevented by**: isolation at the data plane (R-I1/R-I2), scope in every `StateReference`, leak tests in CI (§20, §35). **Residual**: derived stores (embeddings) can leak semantics even when identifiers are filtered. **Falsifier**: a shared-memory design that passes adversarial cross-tenant retrieval tests *and* has a documented sharing policy (then sharing is intentional, not accidental).  ### NEG-7 TOCTOU — precondition true at check, false at effect **Scenario**: agent checks inventory ≥ 1, plans shipment, executes after another order consumed the item. **Mechanism**: check and act are not atomic; no reservation/conditional write. **Prevented by**: pre-effect refresh + `expected_revision`-based conditional write (or an explicit reservation/lease) + `refresh_before_effect=true` for irreversible writes (§14.4/§15.3). **Residual**: for commands without conditional semantics, only serialization or idempotent compensation helps. **Falsifier**: a target API that performs its own atomic check-and-act, making harness preconditions redundant.  ### NEG-8 RETRY_DUPLICATION — retry produces a duplicate side effect **Scenario**: the effect request times out (`UNKNOWN_COMMIT`); the runtime retries with a *new* idempotency key and creates a second payment/order. **Mechanism**: no stable `effect_id`; no ledger reconciliation; `UNKNOWN_COMMIT` treated as "failed". **Prevented by**: `effect_id_derivation`, ledger lookup before retry, `on_unknown_commit= RECONCILE_VIA_LEDGER` (S18/S19/S16). **Residual**: idempotency keys don't protect against logically-distinct duplicates (double-click) ⇒ requirement that the key derives from a stable logical operation. **Falsifier**: a target system that provides exactly-once semantics across a timeout window (then the ledger is convenience, not necessity).  Cross-cutting observation `[INFERENCE]`: in all eight examples the *state existed and was readable* — the failure came from missing **authority, freshness or commit semantics**, not from missing data. That is the core justification for this entire research thread.  ---  # 33.
