## 1. EXECUTIVE RESEARCH CONCLUSION

### 1.1 Robust findings (highest confidence)

**F1 — The boundary between "probabilistic discovery" and "deterministic execution" is enforceable, not merely rhetorical.**
Direct empirical evidence from LLM-agent security research demonstrates that inserting a *deterministic* enforcement layer between LLM decisions and tool execution measurably reduces harm. Progent represents privilege as a security policy consisting of symbolic rules over tool names and arguments; these rules specify which tool calls are allowed for task completion and which unnecessary ones are blocked for security, and every tool call is checked against such a policy through a deterministic procedure, enforcing the principle of least privilege. Ablation-style evaluation shows that this deterministic layer reduces attack success rate from 41.2% to 2.2% on the AgentDojo benchmark while preserving high utility. This is EMPIRICAL_RESULT for the *existence* of the boundary; it is not yet evidence for a *specific contract schema*.

**F2 — Deterministic policy enforcement must be *dynamic* (per-step, context-sensitive), not static.**
Progent maintains a per-step policy that evolves as new information arrives: at step i, the gating privilege control policy is Pi, which enumerates exactly which tool calls the agent may issue at that step. The initial policy P1 is derived from the user's task, and an LLM-based updater reasons about both task context and execution context. Critically, updates are constrained: each proposed update is determined by an SMT solver to be either a narrowing (applied automatically) or an expansion (requiring explicit approval), ensuring that the agent's effective action space can only shrink without approval (monotonic confinement). This is a **direct empirical + partial formal result**: LLMs may *propose*, but only bounded, formally analyzable transformations may execute without human approval.

**F3 — Existing capability protocols (MCP) provide identity and I/O schemas but explicitly do *not* provide semantic contracts, effect declarations, or authorization semantics.**
The MCP protocol allows servers to expose tools that can be invoked by language models; tools enable models to interact with external systems, and each tool is uniquely identified by a name and includes metadata describing its schema. But MCP itself explicitly notes that tools represent arbitrary code execution and must be treated with appropriate caution; in particular, descriptions of tool behavior such as annotations should be considered untrusted, unless obtained from a trusted server. Authorization is layered *on top* via a separate spec: the MCP Authorization specification provides a structured method to provide OAuth2-based access control for tool invocation, helping enforce least privileges, user-specific scopes, and multi-tenant separation via Protected Resource Metadata declaring supported scopes. **Implication:** MCP is a *transport + discovery* protocol. It is *not* a Capability Contract in the sense this report requires. Any Enterprise Harness needs a contract layer *above* MCP.

**F4 — "Skills" in the current agent ecosystem are code-and-doc bundles, not typed semantic contracts.**
"Skill" has emerged as a higher-level capability encapsulation distinct from atomic tools, designed to support multi-step, cross-domain task solving; Anthropic formally introduced agent skills defining them as structured multi-file packages composed of workflow instructions, executable scripts, and domain reference files. Skill packages like each synthesized API includes a function signature, implementation, documentation, prerequisite state, and a usage log recording previous executions carry *some* semantic metadata (prerequisite state), but the primary evaluation criterion in current research is executability, not contract-conformance. A revised skill must pass a check before it is trusted as future capability; SkillWeaver constructs web-agent skills as APIs and hones them through practice, generated tests, and documentation updates—useful evidence, though weaker than full semantic verification since passing tests may only show that a function avoids immediate execution failure. **This is a direct citation-supported gap**: the field itself acknowledges that test-passing ≠ semantic validation.

**F5 — Step-level runtime guardrails add real safety value but do not remove the need for compile-time analysis.**
TS-Flow reduces harmful tool invocations of ReAct-style agents by 65% on average and improves benign task completion by approximately 10% under prompt injection attacks. However, existing guardrail systems for LLM agents primarily focus on static content moderation or rely on complete action plans, lacking the ability for real-time, step-level intervention before unsafe tool execution. Runtime step-level guardrails are *complementary to*, not a *replacement for*, compile-time contract validation — they are the last line of defense against emergent, context-derived unsafe behavior.

### 1.2 Robust *non-findings*

- **No direct empirical evidence** in the retrieved literature identifies a *specific* minimum contract schema (fields, types) that is empirically necessary for enterprise reliability. Existing work optimizes for either (a) security/privilege at runtime (Progent, ToolSafe) or (b) skill acquisition/composition (SkillWeaver, ASI). The *contract-field ablation* this report requires is **ABLATION_EVIDENCE_MISSING**.
- **No direct empirical evidence** in the retrieved literature validates a multi-stage IR (Logical → Physical) for agent harnesses. Any recommendation here is INFERENCE from compiler engineering and database query planning.
- **No empirical evidence** exists for a specific effect-system taxonomy in agent harnesses. Effect systems are transferred from PL theory as ENGINEERING_PRACTICE + INFERENCE, not as validated agent practice.
- **No head-to-head study** in the retrieved literature compares "compiled harness" vs. "state-machine-only harness" vs. "ReAct + guardrails" on the same benchmark under identical adversarial + reliability conditions. This is an **OPEN_QUESTION**.

### 1.3 Bottom-line architectural recommendation (with epistemic caveat)

The **smallest defensible architecture** consists of five *separable* but *not necessarily distinct-artifact* layers:

1. **Discovery Layer** (probabilistic, LLM-driven, MCP-based)
2. **Capability Contract Layer** (typed I/O + declared effects + permission-requirements; NOT permission grants)
3. **Single normalized IR** (only split into Logical/Physical for Profile C workloads — see §9)
4. **Compiler/Resolver** with a small mandatory pass set (§13) and optional passes gated by risk profile
5. **Runtime with JIT authorization + step-level guardrail + postcondition validator**

The *degree* to which each layer is materialized should be gated by **risk profile** (see §34): low-risk read-only agents do not need a compiled manifest; high-risk side-effectful agents *do*. Uniformly applying the full architecture to every capability is **enterprise bloat** and creates a false sense of security ("security theater") without measurable benefit.

**Confidence:** MEDIUM. The building blocks (deterministic enforcement, typed I/O, provenance, JIT authorization, guardrails) each have independent evidence; their combination as recommended here is DESIGN_RECOMMENDATION, not empirically validated end-to-end.

## 3. TERMINOLOGY / ONTOLOGY

To eliminate the confounding of terms across the retrieved sources:

- **Tool** — a concrete invocable procedure exposed by a server (per MCP: tools enable models to interact with external systems; each tool is uniquely identified by a name and includes metadata describing its schema). Physical.
- **Skill** — a *packaged* higher-level capability: structured multi-file packages composed of workflow instructions, executable scripts, and domain reference files. Bundles tools + prompts + code. Physical.
- **Capability** — an *abstract* semantic action ("send-invoice-email", "read-account-balance"). May be implemented by one or more skills/tools. Logical.
- **Capability Contract** — a machine-readable *specification* of a Capability: identity, typed I/O, preconditions, postconditions, declared effects, permission requirements, failure semantics. **Not** the code; not the grant of permissions.
- **Logical IR (CapabilityIR)** — a normalized, typed, resolver-produced structure describing *what* will be composed and *what* dependencies hold, before physical binding.
- **Physical IR (ExecutionIR)** — a lowered IR after tool/runtime binding, topology selection, concurrency scheduling, and validator attachment.
- **Manifest (ResolvedExecutionManifest)** — a *frozen, canonicalized, hashed, versioned* run instance: pinned contract digests, pinned tool digests, snapshot of resolved policies, embedded validator references, expected state versions. Immutable once frozen.
- **Plan** — the *sequence of intended actions*; in this architecture, a plan is the *content* of the Logical IR, not a separate artifact.
- **Execution Graph** — the runtime instantiation of the Physical IR; nodes are running or completed activities.
- **State Machine** — the durable execution model that owns run state, checkpoints, retries, and compensations.
- **Policy** — a decision procedure (PDP) that answers `{principal, action, resource, context} → decide`. Not embedded in the manifest; *referenced* by policy_snapshot_id.
- **Effect** — a *declared* class of world-change a capability may produce (READ_STATE, WRITE_STATE, NETWORK, TRANSFER_VALUE, DELETE, …). Static, contract-level.
- **Permission** — a *credential-bound authorization* to perform an effect on a resource. Runtime, principal-bound.

**Key distinction (H5 confirmed):** *Effects are declared by the contract*; *permissions are granted by the principal's authority*. An effect declaration is a *promise about what the code may do*; a permission is a *grant that says the doer is allowed to do it*. They must be separate fields and separate lifecycles.

## 5. CAPABILITY CONTRACT FINDINGS

### 5.1 What existing standards give us
- MCP: each tool has a name, description, input schema, and optional output schema — this is **identity + interface**, nothing more.
- MCP Authorization: Protected Resource Metadata (PRM) is a well-known "prm.json" file that declares supported scopes, authorization methods, token introspection, and audience rules; role separation allows the resource server that exposes tools and the authorization server to be fully decoupled — this is **permission-requirement metadata** at the *server* level, not per-capability.
- SkillWeaver: each synthesized API includes a function signature, implementation, documentation, prerequisite state, and a usage log recording previous executions — this hints at **preconditions** ("prerequisite state") but not effects, invariants, or postconditions.

### 5.2 What is missing (INFERENCE from PL, DS, Sec)
- **Effect declarations** — no MCP/Skills field
- **Postconditions / invariants** — no MCP/Skills field
- **Idempotency / retry semantics** — no MCP/Skills field
- **State read/write sets** — partial (SkillWeaver "prerequisite state")
- **Failure classification** — no field
- **Provenance / digest / signature** — no field in MCP tool metadata; must be added at the packaging layer (SLSA-style)
- **Data classification / secret requirements** — no field

### 5.3 Findings-summary

1. Current standards give us a *transport-level* contract (name + schemas + coarse OAuth scopes). They do *not* give us a *semantic* contract sufficient to prove composition safety.
2. The gap must be filled by an *overlay contract* — the Enterprise Capability Contract — which references the MCP tool identity but adds effect, precondition, postcondition, state, failure, and validator semantics.
3. Because tool annotations should be considered untrusted unless obtained from a trusted server, contract fields must be **signed by a trusted authority** (publisher + registry), not asserted by the tool server itself.

## 7. CONTRACT ABLATION DESIGN

Since **no direct empirical field-ablation study exists in the retrieved literature** (ABLATION_EVIDENCE_MISSING), the following is a **methodologically sound proposed ablation plan**:

### 7.1 Setup
- Fixed model, fixed retriever, fixed benchmark suite (AgentDojo + ASB + AgentHarm + a custom enterprise stateful-workflow suite)
- Fixed capability *implementations*, varying only the *declared contract fields*
- Dependent metrics:
  - Attack Success Rate (ASR), Benign Task Completion (BTC)
  - Compile-time-detected error rate (per bug class)
  - Runtime repair rate
  - Replay-reproduction success rate

### 7.2 Ladder

| Rung | Adds | New machine decision enabled | Failure class newly prevented | Redundant with |
|------|------|-------------------------------|-------------------------------|----------------|
| C0 | description only | none (LLM-only reasoning) | none | — |
| C1 | + typed I/O | Type-compatible composition | TYPE_MISMATCH, INPUT_UNBOUND | can subsume examples[] |
| C2 | + requires/provides | Dependency closure | DEPENDENCY_UNSATISFIABLE, UNKNOWN_CAPABILITY | — |
| C3 | + preconditions/postconditions | Static feasibility check; runtime validation | PRECONDITION_FAILED (early), POSTCONDITION_FAILED (caught) | some overlap with input_schema at boundary |
| C4 | + effects | Policy preflight, approval routing, retry safety | EFFECT_NOT_ALLOWED, unsafe retry on non-idempotent effect | partially inferable from permissions_required (weak) |
| C5 | + permissions_required | JIT authorization request generation, deny-fast | PERMISSION_UNRESOLVABLE, over-privileged execution | independent of effects (H5) |
| C6 | + state reads/writes | Race detection, freshness enforcement | STATE_CONFLICT, STATE_STALE | independent |
| C7 | + failure classification + compensation_ref | Automated recovery | COMPENSATION_FAILED (routed to human) | — |
| C8 | + validators (schema, semantic, human_gate) | Deterministic postcondition enforcement | OUTPUT_INVALID, VALIDATOR_FAILED | schema partly redundant with output_schema |
| C9 | + identity.version/digest/provenance/signature | Reproducibility, supply-chain integrity | Silent-drift; substitution | independent |
| C10 | + full enterprise contract | Full lifecycle governance | (all above) | — |

**Ablation-derived hypothesis (falsifiable):**
- For **LOW-risk read-only agents**, C1+C2 (typed I/O + dependency closure) capture ≥90% of composition-safety wins.
- For **MED-risk stateful workflows**, adding C3+C6 (pre/post + state R/W) yields the next largest safety delta.
- For **HIGH-risk side-effectful workflows**, C4+C5+C7+C8+C9 are *each* independently required and none is redundant.

**REVISION_TRIGGER:** If a controlled ablation shows C4 (effects) is fully derivable from C5 (permissions) in practice, H5 must be re-examined and effects may become derived/redundant.

## 8. INTERMEDIATE REPRESENTATION FINDINGS

### 8.1 Function of an IR (from compiler practice)
An IR exists to (a) decouple *what* from *how*, (b) enable *analysis passes* over a normalized structure, (c) make the artifact *hashable and reproducible*, and (d) provide a stable target for *lowering* toward one of many concrete runtimes.

### 8.2 Required IR properties for an Enterprise Harness (INFERENCE from PL + DS)
- **Typed** — nodes and edges carry type information for static checking
- **Normalized / canonicalized** — same logical plan → same IR byte-string
- **Immutable + hashable** — for reproducibility (SLSA-analogous)
- **Serializable** (JSON/CBOR/protobuf) for durable execution replay
- **Diffable** — for local repair and re-authorization decisions
- **Policy-addressable** — every node has a stable ID that policies can reference
- **Validator-friendly** — invariants can be checked by external tools (OPA/Cedar)
- **Replayable** — deterministic reduction from IR+state → run

### 8.3 The critical distinction — retrieval edges are NOT dependencies
- A retrieval bundle may include Capability X because it *scored high semantically*.
- This does **not** create a dependency. The IR must **prune retrieval-only edges** during normalization.
- A **logical dependency** exists iff (a) an output of A is bound to an input of B, or (b) B's `state.reads` overlaps A's `state.writes`, or (c) an explicit control edge is present.
- A **physical execution dependency** additionally reflects tool locality, resource ordering, batching.
- An **authorization condition** is *not* a graph edge — it is a *gate on a node* (see §17).

## 9. IR LAYERING DECISION — one IR vs multiple?

**Evidence status:** DESIGN_RECOMMENDATION (INFERENCE from compiler engineering and database query optimization). No agent-domain empirical study.

### 9.1 Argument for a single IR
- Simpler implementation
- Fewer opportunities for translation bugs
- Fewer artifacts to hash and version
- Sufficient for the common case (LOW/MED risk)

### 9.2 Argument for logical + physical
- Optimization boundaries are cleanest (Volcano/Cascades pattern in DB systems)
- Physical runtimes are *many* (Temporal, Step Functions, Argo, custom durable execution) — a Logical IR portable across them prevents lock-in
- HIGH-risk workflows benefit from *separately auditable* logical intent vs execution plan
- Local repair on physical IR does not require re-planning at logical level

### 9.3 Recommendation (profile-gated)

| Profile | Recommended IR layering |
|---------|-------------------------|
| A (LOW-risk read-only) | **Single normalized IR = "PlanIR"**. No physical layer; direct call. |
| B (MED-risk stateful) | **Single CapabilityIR + a Manifest** (freeze/hash). Skip a separate Physical IR. |
| C (HIGH-risk side-effectful) | **Logical CapabilityIR → Physical ExecutionIR → ResolvedExecutionManifest** — three layers, each hashed. |

**Falsifier:** If a controlled study shows Profile C reliability is equivalent under a single-IR compiler, drop the physical layer.

## 14. TYPE / CONTRACT CHECKING MODEL

Applying PL foundations (PL1–PL3) as INFERENCE:

### 14.1 What is statically decidable in the compiler
- **Structural type mismatch** (Output A ≢ Input B under schema unification) — decidable
- **Undeclared write to state** — decidable if `state.writes` is exhaustive (contract discipline)
- **Two parallel nodes writing same state resource** — decidable (write-set intersection under scheduler plan)
- **Read-only workflow containing a WRITE effect** — decidable (effect-set inclusion)
- **Effect not in workflow's authorized effect set** — decidable
- **Irreversible effect without approval gate** — decidable (presence of `human_gate` for effects marked IRREVERSIBLE)
- **Retry on non-idempotent effect** — decidable (retry_policy vs idempotency field)

### 14.2 What is *not* generally statically decidable
- **Secret flow through arbitrary transforms** — undecidable in general (Rice's theorem). Requires *conservative* information-flow types (over-approximation) or runtime taint tracking. Recommendation: use *labels* not *proofs*.
- **Value-dependent preconditions** — require refinement types or runtime evaluation.
- **External-system state that a contract cannot fully predicate** — runtime concern.

### 14.3 The pragmatic contract-checking regime
- **Simple, structural, well-typed by default.** Refinement/dependent types are OPTIONAL and gated by risk profile.
- **Effect algebra** = flat lattice of effect classes with monotone join. This is the *minimum-viable effect system* (see §15).
- **State typing** = read-set + write-set + expected_revision. This is *not* full separation logic; it is CAS-compatible bookkeeping (DS3).

## 15. EFFECT SYSTEM MODEL

**Epistemic status:** INFERENCE from PL1. No direct empirical validation in agent literature.

### 15.1 Effect lattice (minimum viable)

```
PURE
├── READ_STATE                      (internal, owned state)
├── READ_EXTERNAL                   (external system reads)
├── NETWORK                         (network I/O)
├── WRITE_STATE                     (internal state mutation)
├── WRITE_EXTERNAL                  (external system writes)
├── SEND_COMMUNICATION              (email, SMS, notifications)
├── DELETE                          (subclass of WRITE_*)
├── TRANSFER_VALUE                  (financial, subclass of WRITE_EXTERNAL)
├── DEPLOY                          (infrastructure change)
├── CHANGE_PERMISSION               (IAM change)
├── ACCESS_SECRET                   (secret read)
├── EXPOSE_DATA                     (data classified > ambient)
└── IRREVERSIBLE                    (orthogonal marker; may co-occur)
```

### 15.2 Rules
- **Node effects are declared, not inferred.** LLM may *suggest*, but declared effects are the source of truth used by the compiler. Runtime step-guardrail (ToolSafe-style) is the counter-check that a call has not exceeded declared effects.
- **Workflow effect set = ⋃ (node effect sets).** No cancellation. A "read then delete" is not a "read".
- **Policy operates on the aggregate.** Preflight: "does this workflow contain any effect the *task-mandate* forbids?"
- **IRREVERSIBLE forces human_gate.** Compiler invariant: `IRREVERSIBLE ∈ effects → validation.human_gate ≠ null`.
- **Retry safety:** `retry.max_attempts > 1 ∧ WRITE_* ∈ effects → idempotency ≠ NONE`.

### 15.3 Compile-time answers to Stream 7 questions
- "Can policy prove `this workflow writes externally`?" — YES, via effect aggregation.
- "Can the model choose a cap whose effects exceed task-mandate?" — Compiler rejects via effect-inclusion check against the task's *effect budget* (task metadata field, orthogonal to contracts).
- "How prevent hidden side-effects?" — (a) contract linting during release (require declared effects to be validated against static-analysis of the code where possible; open problem for opaque MCP tools); (b) runtime guardrail per S2.

## 16. STATE SEMANTICS

For each state class:

| State | Owner | Authoritative source | Consistency | Mutation | Rollback |
|-------|-------|----------------------|-------------|----------|----------|
| Working Context | Run | Runtime scratchpad | Serializable per-run | Node-local, then merged | Checkpoint |
| Run State | Runtime | Durable execution engine (Temporal-like) | Linearizable | Event-sourced | Replay |
| Workflow State | Application | Business DB / CAS store | Optimistic CAS (`expected_revision`) | Compensating tx (Sagas, DS2) | Compensation |
| Artifact State | Artifact store | Content-addressed store (Bazel/Nix-style) | Immutable-by-hash | Append-only | N/A |
| Environment State | External | System of record | Best-effort | External API | External compensation |
| Policy State | PDP | Policy store + snapshot | Snapshotted per compile | Versioned rollout | Snapshot rollback |
| Memory (agent memory) | Agent | Vector/kv store | Application-defined | Append + reindex | Application-defined |
| Registry State | Governance | Registry (SLSA-style) | Immutable versions | Signed publishes only | New version supersedes |

### 16.1 Compile-time vs runtime split
- **Compile-time (from contract `state.reads`/`state.writes`):** static write-write conflict detection, over-approximation of read-set for freshness policy.
- **Runtime (from actual state):** current revision fetch, CAS on writes, retry-on-conflict decision, snapshot-for-replay.

### 16.2 Race detection (H7 formalization)
Given nodes `N` with concurrent scheduling group `G ⊂ N`:
- INVARIANT: `∀ ni, nj ∈ G, i≠j : ni.writes ∩ nj.writes = ∅`.
- This is decidable at compile time given exhaustive `state.writes` declarations.
- INFERENCE: this is analogous to *data-race freedom by construction* in region-based / linear type systems.

## 17. AUTHORIZATION INTEGRATION

### 17.1 Model
- **Contract carries:** `permissions_required` (a *description* of scopes) — never `permission_granted`.
- **Compile-time:** *policy preflight* — evaluate a *shape question* against a policy *snapshot*: "Given a hypothetical principal with these attributes, could this manifest ever be authorized?" This is a **fail-fast**, not a grant.
- **Manifest carries:** `policy_snapshot_ref`, `authorization_request_template`, `preflight_decision_ref`.
- **Runtime (JIT):** for each effectful node, at the moment of execution, the enforcement plane calls the PDP with the *concrete* {principal, action, resource, context}, obtains a decision, and (if permitted) mints a **short-lived, resource-scoped credential** (OAuth-style) — aligned with the MCP Authorization specification providing OAuth2-based access control for tool invocation, helping enforce least privileges, user-specific scopes, and multi-tenant separation.

### 17.2 Why JIT (H13, C10)
- State-of-world may change between compile and execute (revoked access, principal delegation change).
- Preflight-only authorization suffers from **TOCTOU** (time-of-check vs time-of-use) — a classic OS security failure mode.
- Progent's key innovation is its ability to adapt to the agent's state; traditional static permissions are insufficient for agents that process untrusted data, and Progent's dynamic update mechanism ensures that privilege levels are adjusted in real-time based on information the agent has encountered — this is direct evidence that *static* preflight is insufficient.

### 17.3 The layered authorization decision
1. **Coarse (compile-time preflight):** categorical effects vs task-mandate → BLOCK or CONTINUE
2. **Fine (JIT):** concrete PDP call → DECISION per node
3. **Runtime step-level guardrail (ToolSafe-style):** contextual anomaly detection over interaction history — TS-Guard proactively detects unsafe tool invocation actions by reasoning over interaction history and assessing request harmfulness and action–attack correlations; TS-Flow utilizes TS-Guard's interpretable safety judgments to guide agent behavior
4. **Post-execution validation:** postcondition + effect confirmation

**Authorization is a gate on a node, NOT an edge.** Encoding it as an edge would misrepresent it as a data/control dependency and would fail to model the runtime nature of the check.

## 20. RECOMPILATION / LOCAL REPAIR MODEL

### 20.1 Change classes and their responses

| Change | Local rebind allowed? | New manifest revision required? | Re-authorization required? |
|--------|-----------------------|--------------------------------|----------------------------|
| Tool endpoint changes but digest unchanged | Yes | No | No |
| Tool digest changes | No | Yes | Yes for effectful nodes |
| Contract version changes within pinned range | No | Yes | Yes if permissions/effects changed |
| Contract version changes outside pinned range | No | Yes (re-resolve) | Yes |
| State snapshot refresh (`expected_revision` bump) | Yes (data change only) | No | No |
| Policy snapshot changes | No | Yes | Yes |
| Retry on transient failure with same input | Yes | No | No |
| Alternative capability substituted per `alternatives` | No | Yes (subgraph revision) | Partial (only affected nodes) |
| Human intervention modifies plan | No | Yes | Yes |

### 20.2 Principle (from H12)
- **Any semantic change → new manifest revision.** The revision references the parent manifest hash (chain of provenance).
- **Data-only changes** (state freshness, retry with identical inputs) do not require a new revision.
- **Partial recompilation** is permitted: an unaffected subgraph retains its prior validation flags; only the *dirty closure* is re-validated.
- **Re-authorization** must always occur for nodes whose {effects, resources, principal, policy_snapshot} changed.

## 21. REPRODUCIBILITY CONTRACT

### 21.1 Three tiers (must be distinguished)

- **STRUCTURAL** — same inputs produce byte-identical manifest hash. Fully achievable for the deterministic passes (§13). **Required for audit.**
- **BEHAVIORAL** — same manifest + same environment + same state produces same observable side effects. Achievable modulo external non-determinism (clocks, IDs); requires idempotency keys and state snapshots.
- **STATISTICAL** — LLM-driven decisions (retrieval, planning suggestions) reproduce *up to a distribution*. Not deterministic in general.

### 21.2 Frozen inputs required for replay

| Input | Required for | Storage |
|-------|--------------|---------|
| Task digest | All three tiers | Manifest header |
| Retrieval snapshot (indexed IDs) | Statistical → Structural (of downstream) | Registry snapshot ref |
| Contract set + digests | Structural | Manifest header |
| Tool digests | Structural + Behavioral | Manifest header |
| Policy snapshot | Structural + Behavioral | Manifest header |
| State snapshot ref (`expected_revision`) | Behavioral | Manifest per-node |
| Resolver + compiler version | Structural | Manifest header |
| Model + version + sampler params | Statistical | Retrieval snapshot metadata |
| Validator versions | Behavioral | Manifest per-validator |
| Runtime image (OTel, executor) | Behavioral | Manifest header |

**Note:** "temperature 0" is *not* reproducibility. Numerical determinism of LLM inference depends on kernels, batching, hardware. Statistical replay requires multi-run distributions, not single-run byte-equality. (Anti-bias gate.)

## 22. VERSIONING / PROVENANCE MODEL

**Approach:** apply SLSA + in-toto (SC1/SC2) principles to skill packages.

- **Skill package** = `{ SKILL.md, contract.yaml, code/, validators/, tests/, schemas/ }` bundled as a **content-addressed artifact**.
- **Digest = SHA-256 of canonicalized package.**
- **In-toto layout** describes the pipeline: source → build → sign → publish.
- **Signature** by publisher key attested via Sigstore-style transparency log.
- **Registry entry** = `{ capability_id, version, digest, publisher, in-toto attestations[], lifecycle_state }`.
- **`skill@1.2.3` alone is not sufficient identity;** every reference in a manifest must include the digest (as in Nix / Bazel MODULE.bazel with `integrity` hashes).

**Contract-schema evolution:**
- Contracts are versioned separately from code (`contract_schema_version`).
- Backward-compatible additions (new optional fields) → minor bump.
- Breaking changes (new required fields, effect additions) → major bump + full re-resolution.

| Durable execution | Temporal, AWS Step Functions, Argo, Dagster | State, retry, compensation | Semantic contract | Direct as runtime target | ExecutionIR → workflow definition |
| Compensation | Sagas (DS2) | Long-running transactions | Contract-level validity | Direct | compensation_ref field |
| Observability | OpenTelemetry | Traces, metrics, logs | Semantic meaning | Direct | Standard OTel scope per manifest |
| Provenance | W3C PROV, SLSA, in-toto | Build integrity, attestation | Runtime authorization | Direct at packaging | — |
| Content-addressed artifacts | Nix, Bazel, OCI digests | Reproducibility | Semantic contract | Direct | Digest all skill artifacts |
| Dependency resolution | Cargo, npm, pip lockfiles, Nix | Version resolution | Effect / permission | Adapt | Lockfile-per-manifest |
| Execution isolation | WASM, containers, gVisor, Firecracker | Sandboxing | Contract semantics | Direct | Per-tool-server |
| Compiler IR pattern | LLVM, MLIR (multi-level IR) | Pass architecture, lowering | Domain semantics | Analogy | Design pattern |

**No single tool provides an Enterprise Capability Contract or a compiler for it.** The overlay layer must be built.

## 28. EXAMPLE COMPILATIONS

### 28.A Read-only single capability (Profile A)
- **Task:** "What is the balance on account 42?"
- **Candidates:** `account.balance.read@2.0.0`, `account.summary.read@1.4.0`
- **Contracts:** both READ_STATE + READ_EXTERNAL; typed `{account_id} → {balance}`
- **IR:** single node, no dependencies
- **Compile checks:** IDENTITY, TYPE_CHECK, IO_BIND, EFFECT_ANALYSIS (all reads), PERMISSION_DERIVATION (`account:read/42`), CANONICALIZE, HASH
- **Policy preflight:** "read on account/42" — permit-shape
- **Manifest:** single-node, no compensation, no approval gate
- **Execution:** JIT auth → tool call → schema validate output → return
- **Profile A architecture:** skip Physical IR; direct execution from CapabilityIR is acceptable.

### 28.B Multi-step data workflow (Profile B)
- **Task:** "Summarize last month's invoices and store the report."
- **Candidates:** `invoice.query`, `invoice.aggregate`, `report.render`, `report.store`
- **Contracts:** read of `invoice/*`, write of `report/{report_id}`; effects include WRITE_STATE
- **IR:** 4 nodes; DATA_DEPENDENCY chain; STATE_DEPENDENCY on `report/{report_id}` (single writer)
- **Compile checks:** type-chain across `invoice → aggregate → report`, write-set analysis (single writer to `report`), idempotency (KEY on `report_id`), retry safety (WRITE + idempotent)
- **Policy preflight:** aggregate effects `{READ_STATE, WRITE_STATE}` — permit-shape
- **Manifest:** 4-node, compensation on `report.store` (delete on rollback), postcondition validators on aggregate schema and stored report existence
- **Execution:** each node executes with JIT auth; on `report.store` failure → retry (idempotent) → if final failure → compensate `delete report/{report_id}` → surface error

### 28.C Side-effectful high-risk enterprise workflow (Profile C)
- **Task:** "Approve refund of $500 to customer 7 and email confirmation."
- **Candidates:** `refund.eligibility.check`, `payment.refund.issue`, `email.receipt.send`, `audit.record.write`
- **Contracts:** TRANSFER_VALUE + IRREVERSIBLE on `payment.refund.issue`; SEND_COMMUNICATION on `email.receipt.send`
- **IR:** 4 nodes; approval gate on `payment.refund.issue` (compiler-forced since IRREVERSIBLE); DATA_DEPENDENCY `check → refund → email → audit`
- **Compile checks:**
  - Effect ⊆ task_effect_budget? — requires task carrying `TRANSFER_VALUE` in budget (else COMPILE FAIL)
  - IRREVERSIBLE ⇒ approval_gate present — enforced
  - Idempotency KEY on `refund` — enforced
  - Compensation for `audit.write` — enforced (append-only, compensation = append-reversal record)
  - Payment refund has *no* compensation (IRREVERSIBLE) — enforced: no compensation_ref allowed, only forward-only recovery
- **Policy preflight:** cross-check that principal *could* hold `payments:refund` and $500 is within delegation ceiling
- **Physical IR:** binds to `payment-gateway-prod`, tool digest pinned, PRM snapshot for OAuth2 scopes pinned
- **Manifest:** signed, immutable; policy_snapshot_id pinned
- **Execution:**
  1. State refresh: verify eligibility unchanged
  2. Precondition check: refund not already processed (state.reads with expected_revision)
  3. Human approval gate (blocking)
  4. JIT PDP: concrete `{principal, "payments:refund", "customer/7:refund/500", context}` → PERMIT
  5. Short-lived token minted
  6. Guardrail (ToolSafe-style) inspects intended tool call vs manifest declaration — must match
  7. Execute refund; postcondition validator confirms external receipt id
  8. Execute email; audit record with full attestation chain
  9. On any step failure: forward-only recovery (do not silently retry TRANSFER_VALUE without new authorization)

## 29. NEGATIVE EXAMPLES — compiler MUST block

1. **Undeclared write.** Capability `report.store` declares `effects: [READ_STATE]` but its code contains a write. Contract lint / release-time check detects (INFERENCE — full detection is limited by tool opacity, but declared-effect vs *retrieval-time-observed-effect* mismatch caught at runtime by step-guardrail). **Blocks:** at release-time when possible; at runtime otherwise.
2. **Retry on non-idempotent side-effect.** `payment.transfer` with `idempotency: NONE` and `retry.max_attempts: 3`. Compiler invariant `NO_UNSAFE_RETRY_FOR_NON_IDEMPOTENT_EFFECT` → COMPILE FAIL.
3. **IRREVERSIBLE without approval gate.** `data.warehouse.drop_table` with effects including IRREVERSIBLE but `validation.human_gate: null` → COMPILE FAIL.
4. **Write-write race.** Two parallel nodes both writing `account/{id}` in same scheduler level → COMPILE FAIL (`NO_UNORDERED_WRITE_WRITE_CONFLICT`).
5. **Effect exceeds task-mandate.** Task budget `[READ_STATE]`, but selected capability declares `[READ_STATE, TRANSFER_VALUE]` → COMPILE FAIL. Even if the LLM's plan is otherwise well-formed, the effect-inclusion check rejects.
6. **Unresolved permission requirement.** Capability requires `hr:read` but principal role has no policy path to `hr:read` → policy preflight FAIL (permit-fast-fail).
7. **Cycle in DAG mode.** Node A depends on B which depends on A → COMPILE FAIL.
8. **Type mismatch across binding.** `n0.output.total: number`, bound to `n1.input.recipient: string` → COMPILE FAIL.
9. **Untrusted contract source.** Contract fetched but signature does not verify against publisher trust anchor → REJECT before resolution.
10. **Policy expansion attempted mid-run without approval.** In-run policy-update proposal from LLM expands allowed tool set. Per Progent's model: each proposed update is determined by an SMT solver to be either a narrowing (applied automatically) or an expansion (requiring explicit approval) → expansion rejected without human approval.

## 31. IMPLEMENTATION BLUEPRINT — Minimal Enterprise Harness Compiler

**Language:** Rust or TypeScript (either is fine; determinism and canonicalization are the actual requirements).

**Structure:**
```
harness-compiler/
├── contract-loader/     # fetch by digest, verify signature (Sigstore-style)
├── resolver/            # normalize, pin identity, resolve versions, closure
├── logical-compiler/    # type-check, IO-bind, state-bind, effect-analysis,
│                        # precondition-analysis, graph validation
├── policy-preflight/    # PDP snapshot query
├── physical-compiler/   # tool-bind, idempotency, topology, validators, failure-lowering
├── canonicalize/        # RFC 8785-style JSON canonicalization (or CBOR)
├── hash-freeze/         # SHA-256 emit; produce manifest
└── invariant-checker/   # runs all compiler_requirements from the prompt
```

**Dependencies:**
- JSON Schema validator (compile-time)
- SMT (Z3) for optional monotonic-policy-update proof (Progent-style)
- OPA/Cedar PDP for preflight
- OpenTelemetry SDK
- Sigstore/Cosign for signature verification
- OCI/registry client for content-addressed retrieval
- Temporal (or equivalent) as default runtime target

**Invariant checks (per compiler_requirements block, formalized):**

- `NO_UNKNOWN_CAPABILITIES`: ∀ n ∈ nodes: n.capability_ref.digest ∈ registry
- `NO_UNRESOLVED_REQUIRED_DEPENDENCIES`: ∀ n: n.requires ⊆ resolved_set
- `ALL_INPUTS_BOUND_OR_EXPLICITLY_DYNAMIC`: ∀ n, i ∈ n.inputs: i.source ≠ ⊥
- `TYPE_COMPATIBILITY`: unifier succeeds on every binding edge
- `NO_UNDECLARED_EFFECTS`: (release-time when tool code available) declared_effects ⊇ statically-observed effects — **limited** for opaque MCP tools (open problem)
- `ALL_EFFECTFUL_NODES_HAVE_PERMISSION_REQUIREMENTS`: ∀ n with effects ⊄ {PURE, READ_STATE}: permissions_required ≠ ∅
- `NO_STATIC_PERMISSION_ESCALATION`: aggregate permissions_required ⊆ principal.granted_scopes ∪ delegation_paths
- `ALL_CRITICAL_NODES_HAVE_VALIDATORS`: ∀ n with WRITE_* or IRREVERSIBLE effect: validators.post ≠ ∅
- `NO_UNSAFE_RETRY_FOR_NON_IDEMPOTENT_EFFECT`: n.retry.max_attempts > 1 ∧ WRITE_* ∈ n.effects → n.idempotency.mode ≠ NONE
- `NO_UNORDERED_WRITE_WRITE_CONFLICT`: ∀ scheduler-level L, ∀ ni, nj ∈ L, i≠j: ni.writes ∩ nj.writes = ∅
- `NO_DAG_CYCLES_IN_DAG_MODE`: topological sort succeeds
- `ALL_APPROVAL_REQUIRED_EFFECTS_HAVE_APPROVAL_GATE`: IRREVERSIBLE ∈ n.effects → n.approval_gate.required = true
- `EXACT_CONTRACT_IDENTITY_PINNED`: every capability_ref has {id, version, digest}
- `MANIFEST_CANONICALIZED_AND_HASHED`: `manifest.hash = SHA256(canonicalize(manifest \ {hash, signature}))`

**Limits of provability (must be documented):**
- Effect over-approximation depends on contract honesty; runtime guardrail is required fallback.
- Full information-flow (data classification tracking through arbitrary transforms) is *not* generally decidable and must be conservative.
- Preflight is *shape*-authorization, not fact-authorization; JIT is the true gate.

## 32. TEST SUITE

- **Unit:** each compiler pass, deterministic (property test: same input → same output byte-identical).
- **Contract tests:** for each contract field, a property that the resolver enforces it (e.g., missing `idempotency` on WRITE with retry → COMPILE FAIL).
- **Property tests:**
  - "For every well-typed IR, the manifest hash is stable across re-runs."
  - "For every manifest, replaying yields identical structural output."
  - "For every retrieval bundle, compilation is monotone: adding a candidate never *removes* validity of the compiled manifest for a smaller subset."
- **Integration:** end-to-end run against a stub PDP + stub tool server + stub state store.
- **Security:**
  - AgentDojo-style prompt-injection suite
  - ASB tool-hijacking suite
  - AgentPoison knowledge-base-poisoning suite
  - Custom: signature-verification failure, digest-mismatch, policy-snapshot tampering
- **Replay:** given a stored manifest + state snapshot, replay must reproduce structural output.
- **Fault injection:**
  - Tool timeout → retry policy honored
  - Tool 5xx → retry, then failure classification
  - PDP unavailable → deny-fast per policy
  - Guardrail false-positive → recovery path
- **Stochastic regression:** N replays with different LLM sampling seeds must all *compile to the same manifest hash* when the retrieval snapshot is pinned.

## 33. OPEN RESEARCH QUESTIONS

- **OQ1.** Is there an *empirical* minimum contract-field set for a given risk profile? (No study currently answers this.)
- **OQ2.** Does a Logical/Physical IR split reduce runtime repair cost or is a single IR sufficient at all risk levels?
- **OQ3.** How can effect declarations be *automatically verified* against opaque MCP tool code? (Currently: trust + step-guardrail.)
- **OQ4.** What is the right expressiveness / decidability trade-off for the policy-update DSL beyond Progent's design?
- **OQ5.** Can compile-time information-flow analysis be made practical for LLM-agent workflows without unacceptable false-positive rate?
- **OQ6.** Under what conditions is a state-machine-only architecture (no compiler) equivalent to a compiled architecture in reliability?
- **OQ7.** How do we validate *semantic* postconditions in a way that is not itself a probabilistic LLM check? (Cross-validation, ensemble, human-in-the-loop are candidates; no clear best practice.)
- **OQ8.** What is the correct compensation semantics for cross-tenant / cross-system side effects (Sagas assume single-DB atomicity semantics that do not hold externally)?
- **OQ9.** How should contract versioning interact with running long-lived workflows spanning contract-schema upgrades?
- **OQ10.** Can retrieval bundles themselves be attested as reproducibility inputs without leaking proprietary index contents?

| **Contract** | identity, discovery, interface, effects (READ-only), permissions_required, output validator | + composition, preconditions/postconditions, state.reads/writes, idempotency, failure_semantics | + full contract (signature, invariants, secret_requirements, human_gate, compensation_ref, cost_hints, eval_suite) |
| **IR** | Single normalized IR (LogicalIR only) | Single CapabilityIR + Manifest | Logical CapabilityIR + Physical ExecutionIR + signed immutable Manifest |
| **Compiler passes (mandatory)** | 1, 2, 6, 7, 9, 10, 15, 19, 20 | + 3, 4, 5, 8, 11, 13, 16 | + 12, 14, 17, 18 (all 20 passes) |
| **Runtime gates** | JIT auth for reads; schema validator | + state CAS, retry-with-idempotency, compensation | + human approval gate, step-level guardrail, monotonic policy update, forward-only recovery for IRREVERSIBLE |
| **Reproducibility** | Structural | Structural + Behavioral (idempotent replay) | Structural + Behavioral + attested provenance chain |
| **Auditability** | OTel traces | OTel + PROV-lite | OTel + full W3C PROV + in-toto attestations |

### 34.2 What the LLM MAY do (all profiles)
- Task interpretation and decomposition (proposal only)
- Retrieval query formulation
- Candidate ranking
- Argument value suggestion
- Policy-narrowing proposals (never expansions without approval)
- Diagnosis of failures for human review

### 34.3 What the LLM MUST NOT do
- Assert contract validity
- Grant permissions
- Waive validators
- Modify a frozen manifest
- Expand policy without approval (per Progent's monotonic confinement — C13)
- Substitute a tool at runtime without re-authorization

### Final epistemic summary

The layered architecture presented here rests on:
- **Direct empirical evidence** for the *value* of deterministic enforcement (Progent) and runtime step-guardrails (ToolSafe).
- **Standards** (MCP + MCP Authorization + JSON Schema + SLSA/in-toto + OAuth 2.1 + Cedar/OPA) for identity, transport, and authorization.
- **Formal foundations** (effect systems, refinement types, capability security, Sagas, optimistic concurrency) as INFERENCE — analogically transferred with acknowledgment.
- **Design recommendations** (contract-field set, IR layering, compiler pass table, three-profile tiering) which are *not* empirically validated as a whole and are marked accordingly.

The single largest research gap is **contract-field ablation**: no study in the retrieved literature isolates the contribution of individual contract fields to enterprise safety metrics. The proposed ladder (§7) is the recommended experimental design to close this gap. Until it is run, all field-necessity claims should be read as **DESIGN_RECOMMENDATION** informed by convergent evidence from adjacent fields.
